# 4단계 — 표시명 변경과 운영 사전 점검

작업일: 2026-10-18 KST.

## 진행 계획

1. 표시명을 `회장님`으로 분리한다. 실명·별칭은 내부 검색/관련성 검증/분류에만 사용한다.
2. 공개 리포트와 HTML의 대상명·기사 제목·분류 이유·제목 근거를 일관되게 치환한다.
   치환 전 제목을 AI에 전달하고 검증하며 통계·분모·캐시는 바꾸지 않는다.
3. 원문 링크와 이미 공개된 소스/이력은 그대로 유지한다. 완전 익명화나 이력 삭제로
   설명하지 않고, 공개 제목이 인명 표기를 치환한 것임을 화면에 알린다.
4. OCI의 Cursor 샌드박스 장애를 읽기 전용으로 진단하고 수집 경로를 제한적으로 재확인한다.
5. 기존 서비스에 영향을 주지 않는 배포 사전 검사·실패 차단을 준비한다. 실제 수집과 모델
   검증을 통과하지 못하면 Pages·정기 실행을 활성화하지 않는다.
6. 테스트·실패·권한이 필요한 잔여 작업을 문서와 OCI wiki에 기록한다.

## 안전 경계

- 실명을 표시용 별칭으로 바꾸는 것이 원문 링크나 공개 Git 저장소까지 익명화하지는 않는다.
- 기존 세 게시 서비스·CLI·인증 파일은 변경하지 않는다. 샌드박스를 끄지 않는다.
- 전역 커널/AppArmor 제한 완화나 예외 권한 추가가 필요하면 변경 범위와 이유를 제시한다.
- 자료 부족·API 실패·모델 실패를 가짜 기사나 임의의 긍정/부정 비율로 대체하지 않는다.

## 표시명 변경 결과

- `target.name`과 별칭·검색어는 내부 검색/분류용으로 유지하고 `target.display_name`을
  `회장님`으로 추가했다. 잘못된 표시명은 실명으로 대체하지 않고 실패 처리한다.
- 공개 JSON의 대상명·기사 제목·AI 이유·제목 근거를 치환한다. 한글 사이 공백, 영문
  대소문자·하이픈·전각 표기도 처리한다. AI 입력과 원본 근거의 검증은 치환 전에 수행한다.
- 표시명 변경으로 근거가 표시 제목의 일부가 아니게 되면 공개 근거를 생략하고 이유를 알린다.
  제목·판단 이유·근거가 치환됐다는 설명과 원문 링크가 대상을 식별할 수 있다는 한계를 표시한다.
- 표시명만 바뀌어도 분류를 다시 호출하지 않는다. 캐시·통계·분모는 원본 기준으로 유지한다.
- README 제목과 GitHub 저장소 설명도 `회장님`으로 갱신했다. 기존 공개 소스·Git 이력·
  내부 wiki의 기존 문서명은 재작성하지 않았다. 원문 링크는 깨뜨리거나 임의로 변경하지 않았다.
- 기존 공개 JSON에 표시명을 소급 적용해 재사용하는 것이 아니라 현재 입력으로 다시 export한다.
  내부 `data/`와 캐시는 비공개 런타임 데이터이며 원본 검색 이름을 포함할 수 있다.

## 운영 사전 검사

`python3 -B -m news_monitor.preflight`를 추가했다. 읽기 전용이며 배포·로그인·서버 설정 변경을
수행하지 않는다. 다음을 검사하고 준비되지 않으면 exit 1로 종료한다.

- 정적 파일 네 개의 허용 목록, 심볼릭 링크/여분 파일 제외, JSON 크기와 공개 스키마
- JSON·HTML 표시 문구의 실명 치환, 실제 원문 URL 보존, 가상 데이터 표시/원시 출력 키 거부
- 기사 수·매체별 집계·논조 비율 재계산과 일치 여부
- 모델·프롬프트 해시, 최근 파이프라인·수집 상태와 데이터 시각의 일치·유효성
- 관련·분류 완료 기사 존재. 실패·0건·보류뿐인 결과는 공개 준비 완료로 보지 않음

이는 산출물의 형식·최신성 검사다. 외부 뉴스의 진위나 모델 품질·인증 성공을 보증하지 않는다.
사람 검토를 필수 단계로 추가한 것도 아니다. 실제 기사·모델 end-to-end 검증은 별도다.

## 실제 진단과 실패 기록

### 수집 API

- 기존 요청 상태를 지켜 20:36 KST에 Mac에서 GDELT 단일 조회를 재확인했으나 HTTP 429였다.
  응답 Date는 현재 시각이었고 Age·Cache-Control·Retry-After·Via·X-Cache 정보는 없었다.
  이것만으로 캐시나 제한의 정확한 범위를 확정하지 않는다.
- 다음 요청 가능 시각은 **20:51:35 KST 이후**로 보존했다. 자동 예약이나 다른 IP로 우회하지 않았다.
- API 조회 중 동시에 로컬 재빌드를 시도했을 때 잠금으로 차단됐다. 조회 종료 후
  `--reuse-collection`으로 재빌드했다. 수집 실패·기사 수/비율 확인 불가·모델 호출 0회를 유지했다.
- 현재 로컬 `dist/`의 표시명은 `회장님`이다. 기사 없는 실패 화면을 실제 뉴스 결과로 게시하지 않았다.
  공개 전 검사는 실제로 `ready: false`/exit 1을 반환했다.

### OCI Cursor 샌드박스

- OCI 여유 용량은 약 25 GiB였고 `/srv/news-monitor`는 아직 없다. 새 계정·프로그램은 만들지 않았다.
- `kernel.unprivileged_userns_clone=1`, `kernel.apparmor_restrict_unprivileged_userns=1`이었다.
  기존 계정의 `unshare -Ur true`는 uid_map 권한 오류로 실패했다.
- 커널 감사 로그에서 `cursorsandbox`가 `unprivileged_userns` 프로파일의 `sys_admin`
  권한 거부로 종료한 기록을 확인했다. 즉, 설치 여부 추측이 아니라 AppArmor 거부를 확인했다.
- 현재 helper는 `wiki-publisher`의 `2026.10.16-e3cb207/cursorsandbox`이며, Cursor용
  `/etc/apparmor.d` 프로파일은 발견되지 않았다. bwrap 미발견만을 원인으로 단정하지 않는다.
- Ubuntu 공식 설명도 사용자 네임스페이스가 필요한 앱에 명시적 AppArmor 허용이 필요함을
  안내한다. 이 신규 분류기의 강제 샌드박스 조건이며 기존 게시기가 고장 났다는 뜻이 아니다.

## 추가 승인 필요 — 아직 적용하지 않음

안전하게 진행할 후보는 **전역 제한을 유지하면서 Cursor sandbox 실행파일에만 한정한
AppArmor 프로파일을 검토·추가하는 것**이다. 이는 새 커널 권한 예외이므로 이번 작업에서는
적용하지 않았으며 사용자 승인 후 진행한다.

- `sysctl` 전역 해제·AppArmor 중지·`agent sandbox disable`은 사용하지 않는다.
- 공유 Cursor helper에 영향을 줄 수 있으므로 적용 대상·소유권·업데이트 경로를 먼저 확정한다.
  사용자 쓰기 가능한 바이너리 경로의 예외가 갖는 위험도 검토해야 한다.
- 승인 후 최소 프로파일만 추가하고 모델 단건·기존 게시기 영향·재부팅/CLI 업데이트 시 동작과
  제거 절차를 확인한다. 서비스/타이머를 바로 활성화하는 승인이 아니다.
- GDELT 429 해결과 실제 뉴스 end-to-end 검증도 별도로 남아 있다.

## 검증

- 새 표시명 회귀 테스트 4개가 먼저 실패/오류를 내는 것을 확인한 뒤 수정했다.
- 총 77개 테스트가 Mac Python 3.14·3.12와 OCI Ubuntu Python 3.12에서 통과했다.
- 원문 URL 보존과 공개 표시 문구 치환, 표시명 변경 시 캐시 유지, 부분 근거 생략,
  유니코드/대소문자/공백, HTML 실명 잔존 차단, 사전 검사 실패 경로를 검증했다.
- Ruff·JavaScript 문법·Git diff 검사 통과. 테스트 자료는 임시 경로에만 만들고 정리했다.
- 기존 세 게시 서비스·인증·계정·CLI·커널/AppArmor 설정은 변경하지 않았다.
  Pages는 비활성 상태이며 새 정기 실행도 없다.
