# 매일 수집·GitHub Pages 배포 계획

작성일: 2026-10-18 KST. 2026-10-19부터 구현 중이며 결과는 [6단계 기록](STAGE-6.md)에 남긴다.

## 목적과 현재 상태

사람이 기사를 고르거나 검토하지 않아도 OCI에서 매일 실제 뉴스를 수집·분류하고,
검증한 정적 화면을 GitHub Pages에 게시한다. 공개 표시명은 `회장님`으로 유지한다.

- 현재 실제 샘플은 Mac에서 수집한 기사 3건·매체 3곳이다.
- 최근 14일, 최대 30건, 매체 5곳 목표이지만 목표 매체 수를 달성하지 못했다.
- 검색 실행이 한 번이고 제목에 인물·회사명이 모두 있어야 하는 조건이 누락을 만든다.
- 재수집 결과가 이전 목록을 대체하므로 전에 확인한 기사가 다음 실행에서 빠질 수 있다.
- OCI의 `wiki-publisher` 계정에서 기존 Codex 로그인과 모델 단건 실행은 확인했다.
  `/srv/news-monitor` 설치·정기 타이머·GitHub Pages는 아직 없다.

## 목표 구조와 일정 제안

`OCI systemd timer → 검색 → 검증·누적 → AI 분류 → 집계 → 공개 전 검사 → Pages`

- 실행 계정은 기존 `wiki-publisher`를 사용한다. 새 사용자를 만들지 않는다.
- 매일 **07:00 Asia/Seoul** 실행을 제안한다. 아직 확정·활성화하지 않았다.
  기존 게시기 정규 시작 시각과 분리하고, 작업 시간 제한과 동시 실행 방지를 둔다.
- 기본 화면은 최근 14일의 검증된 기사 목록이다. **수집일과 기사 발행일을 구분**한다.
  오늘 수집한 과거 기사를 오늘 발행된 기사로 집계하지 않는다.
- 당일 발행 기사 수와 해당 날짜의 논조 비율을 별도로 제공한다.
  0건이면 `기사 없음`, 분류 불가면 `판단 보류`로 표시하며 0% 긍정으로 오해시키지 않는다.
- 날짜별 스냅샷·추세 화면은 후속 단계다. 우선 매일 갱신되는 화면부터 검증한다.

## 수집 확대: 단순 상한 증가보다 누락 감소

1. 인물 한글명·영문명·회사명·회장 직함 등 중립 검색어를 설정 파일의 여러 묶음으로
   분리하고, 코드에서 각 묶음을 실행한다. 프롬프트의 권고에만 의존하지 않는다.
2. 전체 실행 시간·검색 호출·후보 수·분류 호출에 합산 한도를 둔다. 묶음별 실패를 기록하고
   일부 검색 실패는 전체 성공으로 숨기지 않는다. API 제한은 우회하지 않는다.
3. 검색 이벤트로 확인된 원문 URL·제목·발행일을 검증한다. 포털 중복, 위험한 URL,
   범위 밖 기사, 홈페이지·시세·회사 보도자료는 기존 원칙대로 제외한다.
4. 제목의 인물명은 있지만 회사명이 없는 후보도 검토할 수 있도록 관련성 판정 경계를
   개선한다. 동명이인과 일반 회사 기사를 회장 개인 기사로 자동 포함하지 않는다.
   관련성이 불확실한 기사는 보류하고 논조 비율 분모에서 제외한다.
5. 조회 범위 안의 이전 검증 기사와 새 기사를 URL 기준으로 합친다. 원래 발행일·최초
   확인일·최근 확인일·재사용 여부를 구분하고, 이전 기사를 새로 확인했다고 표시하지 않는다.
   손상·구형 스키마·기간 밖 데이터는 누적하지 않는다.
6. 기사 수·매체 수·신규/유지 건수·제외 사유·검색 묶음별 결과를 기록한다.
   5개 이상 매체 확보를 우선 목표로 삼되 뉴스가 없으면 만들거나 날짜를 늘려 채우지 않는다.
7. 전문 통신사·경제지·종합지의 허용된 API/RSS 등 직접 수집 경로는 이용 조건과 자동 접근
   허용 여부를 확인한 뒤 별도 어댑터로 추가한다. 매체 수 목표와 수집원 수를 혼동하지 않는다.

긍정/부정 검색어로 원하는 비율을 만들지 않는다. 기사 건수 비율은 보도량의 표본이며
전체 여론이나 객관적인 평판 지표가 아니다. 동일 이슈의 여러 매체 보도는 별도 기사지만,
이슈 수가 그만큼 늘어난 것으로 설명하지 않는다.

## Pages 배포와 자격 증명

- OCI에는 소스·설정·비공개 실행 데이터·로그를 분리한다. 기존 세 게시기 설정은 수정하지 않는다.
- 공개 아티팩트는 기존 허용 목록의 정적 파일 4개만 사용한다. `.env`, 로그인 정보,
  원시 모델 출력, 내부 실명 필드, 실행 로그와 분류 캐시는 업로드하지 않는다.
- 기존 Codex 로그인을 GitHub Actions에 복사하지 않는다. 검색·분류는 OCI에서 실행한다.
- 검토 결과 별도 빌드가 없는 화면이므로 `pages-data` 브랜치 루트를 Pages 게시 소스로
  사용한다. 자체 워크플로를 추가하지 않고 브랜치에는 검증한 정적 파일 4개만 둔다.
  GitHub가 내부적으로 수행하는 Pages 빌드/배포와 Git push 성공은 구분한다.
- OCI의 `news-monitor` 저장소 쓰기 권한은 아직 확인하지 않았다. 기존 다른 프로젝트의
  토큰을 무단 재사용하지 않는다. 권한이 없으면 저장소 전용 배포 키 또는 범위 제한 토큰의
  발급·승인을 사용자 작업으로 남긴다. 비밀 값은 문서·명령 출력·Git에 기록하지 않는다.
- Pages는 공개 샘플이다. `회장님` 치환은 익명화를 보장하지 않으며 원문 링크와 기존
  공개 Git 이력에서 인물을 알 수 있다. 사내 전용 데이터나 담당자 의견은 넣지 않는다.
- 공개 전 검사 실패·수집 실패·0건·분류 실패 시 기존 정상 배포를 빈 화면으로 덮지 않는다.
  최근 시도와 마지막 성공을 운영 상태에서 구분하고, 화면에는 실제 데이터 기준 시각을 남긴다.

## 구현·검증 순서와 완료 조건

1. 누락·누적·부분 실패·합산 예산의 실패 테스트를 먼저 추가하고 수집기를 개선한다.
2. 실제 자동 수집으로 이전 3건 대비 확보량·매체 수·중복·제외 사유를 비교한다.
   수량 증가를 보장하지 않고 실제 결과를 기록한다. 사용자가 기사를 수동 선정할 필요는 없다.
3. OCI에 뉴스 전용 경로와 systemd service/timer를 설치하되 타이머는 비활성 상태에서
   수동 1회 실행한다. 소스/모델/검증 결과와 파일 소유권·권한을 확인한다.
4. 저장소 쓰기 권한을 확인하고 최초 Pages 배포를 검증한다. 공개 URL에서 HTTP 응답,
   실제 기사·비율·링크·모바일 화면·`회장님` 표시·비밀 값 미포함을 확인한다.
5. 실행 시각을 확정하고 타이머를 활성화한다. 다음 예약 실행의 로그와 Pages 갱신까지
   확인한 뒤 운영 완료로 기록한다. 실패 시에는 이전 배포를 유지한다.
6. 코드 버전·설치 경로·유닛·권한·로그 위치·보존 기간·실패/재실행/중단 방법과
   실제 공개 URL을 프로젝트 문서 및 OCI wiki에 남긴다. 로그는 크기·보존 기간을 제한한다.

[6단계 기록](STAGE-6.md)을 기준으로 확인한다.
