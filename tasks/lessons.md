# Lessons

## 2026-10-24: 기술 판단을 사용자에게 떠넘기지 않는다

- 상황: 수집원 실측을 직접 설계·실행하고 근거까지 정리한 뒤 "A/B/A+B 중 무엇으로 할까요?"라고 물었다.
- 사용자 피드백: "그건 나한테 물어보면 안 되지. 네가 제안해서 진행한건데."
- 규칙: 실측·근거가 있는 기술 선택(수집원, 구조, 표시 방식)은 직접 결정하고 근거와 함께 진행한다.
  사용자에게는 권한·비용·계정·약관·외부 공개처럼 사용자만 결정할 수 있는 것만 묻는다.

- 모델이 지켜야 하는 수치 규칙(날짜 간격 등)은 프롬프트로 강제되지 않는다. 운영 입력으로 재현해 확인한 뒤, 검증 게이트는 그대로 두고 코드에서 결정적으로 맞춘다.

- (사용자 정정 10/25) 보고는 사용자가 판단할 수 있게 쓴다. 문제마다 ①무엇이 문제인지(쉬운 말) ②영향(지금·방치 시, 숫자) ③제안(추천안·이유·사용자가 할 일)을 붙인다. 코드명·용어만 나열하거나 "판단 필요"로 넘기지 않는다. 기술 판단은 내가 하고, 승인이 필요한 것만 근거와 함께 묻는다.

- `Persistent=true` timer에 오늘 이미 지난 시각(예: 12:00)을 더하고 timer를 다시 시작하면, 마지막 실행 뒤 그 시각을 놓친 것으로 보고 즉시 실행한다(10/25 16:40 의도하지 않은 게시 1회). 정기 timer 일정을 바꿀 때는 `systemd-analyze calendar`와 마지막 실행 시각으로 즉시 실행 여부를 먼저 따지고, 피하려면 새 시각이 오기 전(마지막 실행과 새 시각 사이)에 설치하고, 피할 수 없으면 실행 전에 사용자에게 알린다.

- (10/25) 사이트맵 제목만 보고 "7시 이후 올라온 소송 기사"라고 예로 들었는데 실제는 8/21 기사였다. 사용자 판단의 근거가 되는 예시는 발행일·수집 여부를 확인한 뒤 든다. 사이트맵에는 몇 달 지난 기사도 실린다.

- (10/26) Cursor 로그인 무효화를 날짜만 보고 "30일 만료로 보인다"고 보고했다가, 같은 서버 ubuntu 계정의 더 오래된 로그인이 살아 있는 것을 뒤늦게 봤다. 원인 추정은 반대 사례(같은 도구의 다른 계정·문서의 유효기간)를 먼저 확인하고, 확인 못 한 것은 추정이라고 구분해 말한다.
